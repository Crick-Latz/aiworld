# 从小说学习认知：阶段、接口与证据

更新：2026-09-10。

## 一、它在项目计划中的位置

历史 P6.0 文档已经提出 Narrative Behavior Mining 与 Behavior Pattern Library，并以文学作品组织了行为模式。现有仓库中的这些材料属于设计与人工抽象。它们没有提供可重放的全文抽取流水线，也缺少章节、原文位置及逐条审核证据，因此本轮不把它们计作已完成的训练数据。

本轮增加 **P6.N0：认知案例证据接口**。它为后续从小说提炼认知模式提供输入、校验与检索边界，运行中保持只读。真实语料可从现在开始准备。

下一步的 **P6.N1：真实小说抽取与影子评估**，安排在 P7 的第一条信息搜索/社会子目标闭环建立之后。那时已有“发现缺口、搜索、询问、协商、履约”的可执行语义，才能检验小说提供的策略是否适用于当前局势。该阶段在 UI 与美术投入之前完成。

通过影子评估后，**P6.N2** 才允许案例对候选策略排序施加有界先验。模型微调属于可选后续路径，启动条件是已经积累足够的合格案例与稳定评估集。当前没有执行微调，也没有宣称已经训练出小说认知模型。

## 二、学习对象

目标是角色处境中的认知与行动关系。例如，一个人缺材料时如何判断求助对象，如何理解拒绝，何时提出交换，以及履约如何改变之后的信任。

每条案例保留 13 个字段：

| 字段 | 含义 |
|---|---|
| `problem` | 角色试图处理的问题 |
| `perceived_situation` | 当时角色感知到的局势 |
| `knowledge_used` | 此次决策实际用到的知识 |
| `available_resources` | 角色可支配的资源 |
| `candidate_strategies` | 至少两个候选策略，推断项单独标记 |
| `chosen_strategy` | 原文中实际选择的策略 |
| `prerequisites` | 实行所需前提 |
| `tool_capability` | 工具与能力关系 |
| `social_dependency` | 对其他角色的依赖 |
| `risk` | 风险与不确定性 |
| `failure` | 已观察到的受阻或失败，未知内容需标明 |
| `adaptation` | 新证据出现后的调整 |
| `long_term_consequence` | 后续影响，尚未验证的推断需标明 |

每个字段必须引用证据 ID。推断字段列在 `inferred_fields`，原文证据则记录 NARRATOR、CHARACTER 或 DIALOGUE 视角及对应主体。审核时尤其需要检查“叙述者知道的事情”是否被误写成“角色当时已经知道的事情”。结构校验器能检查引用与格式；对这类语义准确性的判断仍依赖人工审核和反事实测试。

## 三、当前已实现的离线接口

输入示例见 `lore/cognition_fixture.cases.json`，原文位于 `lore/cognition_fixture.txt`。这段文字由本轮编写，标记为 `ENGINEERING_FIXTURE`。任何工具输出都应保留这个来源类型。真实小说提取项使用 `SOURCE_DERIVED`。

处理过程：

```text
UTF-8 原文片段 + 人工/LLM 结构化抽取
    → DRAFT 案例
    → 审核原文证据和主观视角
    → APPROVED 案例
    → compile_cases.py 校验并编译
    → CognitiveCaseLibrary.load_pack / retrieve
    → ADVISORY_ONLY 建议
```

本轮实现从 APPROVED 案例开始的校验与编译，以及 Godot 内的读取和检索。前面的 LLM 自动抽取器与审核界面属于后续工作。`reviewed_by` 是审核记录，校验器不把它等同于对语义正确性的自动证明。

导入器检查原文 SHA-256、相对路径边界、UTF-8、证据范围和逐字匹配，并校验 13 字段及其证据引用。位置使用从零开始的 Unicode 码点偏移，右端不包含在片段中。UTF-8 字节偏移、JavaScript UTF-16 偏移需要先转换，不能直接混用。

输入的未知顶层字段会被拒绝，避免把 `world_effects` 一类执行指令塞进案例。原文片段上限为 2MB，一包最多 512 个案例；大型语料按章节分批处理。编译后的运行包保留证据指针和解释，省略原文引文。

## 四、运行边界

`CognitiveCaseLibrary.retrieve(problem_id, subjective_context, available_rule_ids)` 只返回与角色已知来源、已知配方及调用方现有规则 ID 相符的建议。

案例中出现鱼群，只能作为历史案例中的情境。当前角色必须已经拥有相应来源信息，检索门才会放行。案例中的工具知识也无法替代当前世界中的物品目录、已知配方或库存。返回值没有执行接口，不能直接创建行动、写角色自传记忆或改动世界事实。

目前案例库通过独立 API 和测试使用。默认 `framework` 配置没有自动加载工程样本，也没有让案例改变 NPC 的实际行为。后续的 SHADOW 集成要单独增加开关，并记录“检索了什么、若启用将建议什么、现有系统最终实际做了什么”。

## 五、进入 P6.N1 的验收条件

首先取得具有明确使用依据的文本，注明书名、版本与章节，保存可定位的原文。提取案例须逐条审核，训练/开发与评估集合按作品或章节隔离，避免用同一片段自证有效。

其次准备可运行的反事实场景。例如，对方已死亡、已经拒绝、资源耗尽或角色尚未听说消息时，候选策略应随前提改变。每次建议必须能还原到当时的主观信息，原作剧情顺序不得成为任务触发器。

最后进行成对实验：相同世界与随机种子下，对比案例建议关闭与影子检索开启。先验证世界事件与行动完全一致，再评估建议的合法性、重复率和语义价值。主动影响行为的实验属于 N2，须单独登记参数与验收标准。

## 六、后续需要的材料

当前无界面框架无需额外材料。真实小说阶段需要 UTF-8 TXT/Markdown 原文片段，注明版本与可使用范围，并提供希望优先学习的认知类型。首批可以集中在一段包含目标、拒绝或交换，以及明确行动后果的章节。只提供书名时，可以讨论概念；逐条证据抽取需要能够定位的文本。

之后选择在线模型时，在本地环境变量或被 Git 忽略的配置中填写凭据。当前交付的运行与测试不需要在线模型。
